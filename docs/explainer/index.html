Meta Global AI Developer Hackathon · solo entry · explainer

A frontier model serves everyone. This makes one yours.

ai-symbiont reads your coding agent's history: its sessions, your pull requests, and the places you corrected it. It finds the mistakes that keep coming back and warns the agent before the next one. A small learner on your own machine decides when to speak, and everything it says is plain prose that quotes what happened.

you › add retry to the webhook handler
symbiont › the last two edits to webhooks/handler.py broke tests/billing
agent › editing webhooks/handler.py …
symbiont › recalled: you rejected exponential backoff here on Oct 12 ("use the queue's retry")

1

The idea in two minutes

Coding agents repeat themselves. They edit the same file three times, run the command that failed the same way last Tuesday, and forget the thing you told them last week. The information that would stop that already exists in the agent's own logs. Nobody mines it.

ai-symbiont is the pipeline that does. A miner reads the logs and marks pain points. A learner watches the agent work and decides at each step whether this moment looks like one that went wrong before. When it does, a short note goes into the chat, and the model decides what to do with it. The sidecar never acts on its own.

Who it is for

Company teams that already hold months of agent-session history, and solo developers with one machine. To a team we say: your sessions are a training set you already own. To a solo developer: one install, the learner runs on CPU, and you need a GPU only if you want the LoRA.

Why a small learner and not a bigger model builder

The design page states the principle: small networks are good at deciding (what to fetch, is this going badly) and bad at storing compressed memories. So we keep the original text in a local store, and the network only picks from it. A note can always quote what happened, because the record it points at still exists.

Fine-tuning a large model per person isn't cheap enough to do for everyone and keep doing as history grows. A learner with about five thousand cells is. hypothesis

What this project doesn't claim expert

We don't claim the real fly wiring improves results. The live network uses random wiring at the fly's published counts, and the FlyWire connectome is an optional download that no code fetches. We don't claim anything about how fast it learns. We don't claim it makes a model smarter at tasks it can't do; our hypothesis is only that it prevents repeated mistakes. We say "plays Freedoom via ViZDoom" and never brand the project as the trademarked game. The design page lists these as anti-goals, and a gate enforces them: scripts/gates/check_claims.py refuses the forbidden phrases.

How it is built

Think of a lab bench with a sealed glass box in the middle. Inside the box sit the records, the miner and the learner. The box has no window to the network, the clock, the disk or any coding tool. Everything that touches the outside world sits on the bench around it: the log readers, the database, the localhost service, the game engine, and the one HTTP client.

in this snapshot

Miner

Pure rules on CPU, with no AI model. Each signal has its own file under src/symbiont/miner/signals/: a failed command, an edit later reworked, a loop, a user correction, a review flag, and blast radius. Every pain point cites the records it came from.

Readers, one per harness

A reader turns one harness's logs into the shared Record. The first reader is OpenHands (readers/openhands.py), and a new harness is one new file plus a registry line. A line the reader can't parse raises ReadError with the file and line, so it never quietly trains on less.

Pure core

The Decider slot and three fillers: counters, similarity search, and the mushroom-body network. State goes in and comes back out; nothing holds it. The unit tests run with sockets disabled.

Route A delivery

A localhost service answers /observe, /recall and /learn. An MCP server exposes one tool, recall(question), and hooks push short notes at session start, on each prompt and after tool calls. The model decides what to act on. We've committed the package rules (service/AGENTS.md, delivery/AGENTS.md), and status says what code exists.

Route B: a personal LoRA

The same pain points, learned into the weights of Muse Glimmer instead of delivered as notes. We build two kinds of pair: recall ("what broke last time I touched X?") and correct (a situation and the corrected action). Every completion quotes the records word for word, never a paraphrase (routeb/dataset.py).

designed

Setup wizard

symbiont setup is a guided terminal flow. It finds your history, lists your projects with session, PR and correction counts, previews the top pain points with their original text, trains on CPU, and installs into your harness. If it can't read a log, it names the file and asks you.

Act 1: plays Freedoom via ViZDoom

The game state becomes text, and the model replies with a strategy made of scripted moves ("walk to the blue door"), each labeled as scripted. An unknown move raises StrategyError, and nothing falls back to "explore". The engine, the model call and the files live in periphery modules.

Act 2: a developer's week on sqlglot

Real bugs from one open-source repository, graded by its own tests, with and without the learner. The task pool and the gold-patch check are done. The first model calibration runs are recorded, and they're incomplete; see results.

The record is the only contract builder

src/symbiont/records/schema.py defines two frozen dataclasses, Record and Provenance, read and written as JSONL. Readers produce them, the miner consumes them, the store keeps them, and the core reads them. Two rules carry weight. Provenance.spark_safe has no default, so we never treat unknown privacy as shareable. And exit_code=None means "not reported", never "succeeded". Task ids in two spellings (owner__repo-123, owner/repo#123) compare equal, and an unrecognized id raises rather than matching nothing.

Why this shape: if the readers, miner, store and core passed loose dicts, a schema change would need edits in several places, and every caller would read the producer's source. The repo calls that failure a Distributed Monolith, and the dataclass contract is the fix.

The one door out builder

Every outbound HTTP call under src/ goes through symbiont.egress.post_json. Its policy, a pure function in egress/policy.py, refuses four things for a remote endpoint: a payload with undeclared provenance, any record with spark_safe=False, a non-https URL, and a host outside the allowed list. Local endpoints (the Glimmer server, the localhost service) accept any provenance, and only loopback or LAN hosts. The logs hold the endpoint, host, byte size and record count, never the text.

Three nets enforce it: a semgrep rule (sym-single-egress) that fails any other network import under src/, an import-linter contract (network-only-through-egress), and the policy tests.

Spark privacy and the hold-out, as code expert

Two kinds of history carry different terms. Public OpenHands trajectories are CC-BY and may reach any model tier. Real human sessions (SWE-chat, the owner's own) are spark_safe=False, and they never reach a tier that may train on them. The local store exposes Store.spark_view() for Spark-bound code, and a read that would return a private record raises SparkPrivacyViolationError. It never filters quietly, because a quiet filter would make a privacy bug look like "no history".

The hold-out rule works the same way. add_records(..., held_out=...) takes the scored task ids as a required argument, and it raises HoldOutViolationError if a trajectory of a scored task tries to enter a store a scored arm reads. Route B's dataset derivation runs the same check before it builds any example.

The learner: a slot, and what fills it

The core doesn't know which learner is loaded. The slot (core/slot.py) takes a Situation: the session so far, the pain points of earlier work, and candidate records to recall. It returns a Decision: a kind of trouble or none, the pain points behind it, up to three records to recall, and the reason when it stays quiet. So you can tell a silent learner from a broken one.

Counters, the reference

The whole rule is a count: this file or command has gone wrong this many times before. It's the bar, and a learner that can't beat it hasn't earned its place. core/counters.py.

Similarity, the other reference

It never warns. It recalls the three past steps that look most like this one, scored by word overlap. It's the cheapest thing that could help. core/similarity.py.

The fly's mushroom body, under test

A learner built on the fly's real circuit, at its published counts. 86 inputs fan out to 5,177 Kenyon cells, each listening to 7 inputs, and only the top 5% fire. A local, dopamine-like rule changes one output weight per cell. There are no gradients and no backprop. established

When trouble follows, the active cells' weights get cut. When nothing follows, they relax back, a tenth as fast. Overlap limits the learning, so a step that shares few active cells with a punished one barely moves. core/mushroom.py.

The 86 inputs, and why notes never mention them builder

core/features.py turns a situation into 86 numbers: 6 position buckets, 6 action kinds, 18 file-history counts, 24 signal-history cells, 8 command families, 8 outcome-trail cells, 2 lines-added buckets and 14 hashed command tokens. The layout is fixed so the mushroom body's input count holds. The feature names exist for the dashboard only. A note to a model is domain prose ("the last two edits to this file broke tests"), never a score, a feature name, a threshold or a cell activation. That rule is binding in the repo's CLAUDE.md.

What a Decision carries, and the warning budget expert

Decision(trouble, why, recall, reason_none, risk). risk is for evaluation only, and it's hidden from repr so it can't leak into a note. The live operating point is a warning budget (core/warning_budget.py), a share of steps allowed to warn, calibrated on the training split and enforced live. The trouble threshold doesn't set it. The default is 0.15 over 20 steps, which is three warnings per twenty steps. established

Every admitted warning gets settled. If its signature hasn't followed within 5 steps, it becomes a false-alarm outcome, and the learner learns from it. For the fly, that means the pattern that warned relaxes and its risk falls. Counters have no such decay. We added the budget because the offline selection showed that balanced accuracy let each learner pick its own warning rate, and the fly picked a very high one. The next section has the numbers.

How it is measured

Before we believe any learner, we replay it over recorded history and score it against the plain counters on the same steps. At every step we ask one thing: will a pain point land in the next five steps? A learner that flags is right if one does, and wrong if none does.

Four habits that make a number trustworthy

Pre-registration

A scored run needs a frozen, committed file in prereg/. It fixes the split, the seed, the labels, the metric and the decision rule before any test number exists. Amendments are new dated files, never edits, and the runner (eval.require_frozen) refuses a scored run without one.

Roles on every row

Each result row carries a role: floor, ceiling, reference or under test. The table renderer and the dashboard exporter refuse a fly row without the counters row beside it.

Hold-out

No trajectory of a scored task enters a store that a scored arm reads. The store takes the held-out ids as a required argument and raises on a violation.

Claim tags

Every quantity in docs/, prereg/ and the results notes carries measured, established or hypothesis, and a gate (check_claims.py) fails the commit otherwise. This page passes that gate.

The data and the split builder

The history is 2,678 OpenHands trajectories on 275 sqlglot tasks from the public nebius SWE-rebench set (CC-BY-4.0). We read them through readers/openhands.py into 366,185 records. measured

We split by task id, never by trajectory, so every attempt at a task lands on the same side: 193 train tasks and 82 test tasks, test fraction 0.3, seed 20261029. measured

The split is random over tasks rather than forward in time, so the result measures whether similar trouble recurs elsewhere in the corpus. It doesn't measure prediction of future tasks. established

We never commit raw rows. The dataset downloads on setup, and the repo publishes counts, ids and labels only.

Metric, calibration and the decision rule, exactly expert

Replay. Each learner replays the train sessions online and learns from the outcomes. Then it continues through the test sessions with the state it ended on. We score only the test-session steps, 101,755 of them. measured

Label. A pain point, after hub and scratch-file filtering, falls at steps t+1 to t+5 of the same session. The learner never sees the current session's pain points, because we place them after the fact.

Primary metric. Balanced accuracy of the binary flag, which equals AUROC with ties as half: (TPR + TNR) / 2. A learner that never flags scores 0.5. established

Calibration on train only. We pick the counters' min_count from {1, 2, 3, 4}, and the fly's trouble threshold from {0.5, 0.6, 0.7, 0.8, 0.85, 0.9, 0.95}, once per wiring seed, for three seeds. Both landed on a grid edge. The counters chose 4 on a flat train curve (0.526 to 0.527), and the fly chose 0.5, the lowest value listed, for all three seeds. measured

Rule (G6). The fly goes live only if its seed-averaged balanced accuracy is at least the counters' plus 0.02 and the 95% task-level bootstrap interval of the gap excludes zero. Otherwise the counters go live. The bootstrap draws 2,000 resamples over tasks with seed 20261029. There's no other outcome and no re-run after seeing the table. established

Hub rule. A repo module that more than 50% of the test files import is a hub. Breaking a hub isn't a mistake and isn't a label. We found one hub module at the frozen checkout. measured

Results so far, including the ones that hurt

We've committed two offline analyses. The first picked the live learner by a frozen rule. The second ran after the owner saw how often that learner spoke, and it asked what a warning is worth. The short version: the fly beat the counters on the pre-registered metric, mostly by warning far more often. At an equal warning budget it's more precise, and it's still below break-even, like every learner here. No learner has earned its warnings yet on these recorded steps.

What is a warning worth? The equal-budget analysis

This one is exploratory and post hoc. We'd already used the test split once, so these numbers can't overturn G6 and carry no decision rule. They put every learner at the same warning budget, calibrated on train, and count what a wrong warning costs. Net benefit per 100 steps is true warnings minus c times false warnings, per 100 steps. The cost c is an exchange rate we assume; nobody has measured it. hypothesis

How to read it, and what it doesn't say expert

Every learner sits below zero net benefit at every budget and every cost we tried. Break-even precision is 0.33, 0.50 and 0.67 for c = 0.5, 1 and 2, and the best precision we saw is about 0.23. Staying silent beats every row on these recorded steps. That's about these steps and these assumed costs; it isn't a verdict on live use. measured

The train threshold doesn't transfer exactly. At a nominal budget of 0.10, the counters flag 0.178 of test steps and the fly 0.087. The counters' risk is a raw count that grows with history, so a threshold fixed on the shorter train replay over-flags later. The fly's weights relax, so its risk falls. Part of the net-benefit gap is that the counters spend more warnings than the budget and the fly fewer. hypothesis

So the live operating point is a warning budget, and the Act 2 pre-registration freezes the budget, precision at the budget and net benefit as primary and secondary metrics before any scored run. Balanced accuracy alone lets each learner choose its own warning rate.

We also record the honest state of Act 2. The sqlglot task pool holds 268 tasks of 294 candidate rows (26 excluded for gold patches of 60 or more changed lines), and the gold patch resolved every one of the 268 in the shared image. measured

The first open-weights calibration runs (Muse Glimmer in mini-SWE-agent, 2 tasks, 2 runs) both hit the 30-step limit without submitting, at a mean wall time of 335 s per run. So the calibration band is "incomplete", and no scored Act 2 run exists yet. measured

Both analyses ran on a CPU host with no GPU. The G6 run took 2,044 s of wall clock for three learners and three wiring seeds over 101,755 scored steps, and the budget analysis took 1,243 s. measured

How it is tested

The repo treats software decay as the enemy and names ten ways it happens. Each quality gate exists to make one of them impossible. The standard is the long version, and this is the short one.

Airplane mode

Every unit test without the periphery mark runs with sockets disabled. tests/conftest.py installs a function that raises AirplaneViolationError on any socket use. So the pure core can't pick up a network dependency by accident, because the first test that needs one fails. The suite has 923 collected tests and a committed count floor of 240 that only the owner may lower. measured

The gate catalog, by the failure it prevents

  • Secrets and private infrastructuregitleaks with repo rules for API keys, private addresses, hostnames, home paths, e-mail and phone patterns. Silent Fallback · Black Box
  • Owner identifierscheck_private_terms.py, with the terms file kept outside the repo; it fails closed when the file is missing. Silent Fallback at the publish boundary
  • Path guardcheck_paths.sh: no data, transcripts, weights, WAD files or files over 1 MB. Leaky Narrative at the repo boundary
  • Result-file contentcheck_results_content.py: results hold counts, ids and labels only; value shapes are allowlisted. Leaky Narrative at the repo boundary
  • Edit-time secrets guardA Claude hook runs gitleaks on the text being written, the earliest stage a secret can be caught. Silent Fallback
  • Egresssemgrep sym-single-egress and sym-no-prompt-logging, plus the import-linter contract. Distributed Monolith · Silent Fallback · Black Box
  • Publish checkcheck_export.sh exports HEAD and runs every sensitive-data check on the exported files, so nothing hidden by a history baseline or a diff-only scan slips through. Silent Fallback at the publish boundary
  • Lint and formatruff. Forensic Coding · Fossil Comments
  • Complexity, nesting, file lengthlizard plus AST checks. Pure core: 30 lines and CCN 10 per function, 5 parameters, nesting 3, 400-line files. Waivers are delete-only. God Method · God Class
  • Namingcheck_naming.py: no handle, process, Manager, utils; no function with two bool parameters. Forensic Coding · Leaky Narrative · God Method
  • Architectureimport-linter contracts in .importlinter and tests/test_boundaries.py; the two must agree. Infected Core · Distributed Monolith
  • Testspytest, zero skips, a count floor in scripts/gates/test-floor.txt. Paper Tiger
  • Claims and resultscheck_claims.py (every quantity tagged, forbidden phrases) and check_results.py. Paper Tiger · Silent Fallback
  • The gates guard themselvescheck_gate_integrity.py fails on an added waiver, a lowered floor, or any edit to a gate script, hook or config unless that commit's own message carries a GATE-CHANGE trailer. Silent Fallback
The import rules as a contract builder

.importlinter states three contracts. Layers: records below miner below core; a lower layer never imports a higher one. Airplane test: the pure core never imports sqlite3, socket, http, urllib, subprocess, time, vizdoom, transformers, peft, mcp, or any periphery package. Egress: only symbiont.egress reaches the network. The file names its own load-bearing line, include_external_packages = True. Without it every external module is ignored in silence, and the purity contract passes forever.

Packages that don't exist yet appear as wildcards, so the contract already covers them. A test fails when a package under src/symbiont is missing from the file, so nobody forgets one at merge.

Fix the finding, never the gate expert

The repo's rule for agents and humans alike: don't loosen a threshold, add a whitelist line, add a noqa without a reason, delete a failing test, or bypass a hook. We fix a false positive in the rule, with a fixture that proves it. Phase 1 holds changed files to the full bar and counts the existing offenders in scripts/gates/baseline.json for a later cleanup, so the bar never moves down to meet the code.

Two more guards are worth knowing. The pre-push history scan compares the whole git history with a committed baseline of findings we've already published. That file reports the old findings, never hides them, and any new one fails. And tests/conftest.py strips the git environment a hook exports, so a test's throwaway repository can never touch the real one.

What isn't done, as of this snapshot

We wrote this on the day of the first public snapshot, so a judge can check every line against the tree.

  • Route A delivery code. The service, the MCP server, the hooks and the wizard have their package rules committed (src/symbiont/service/AGENTS.md, src/symbiont/delivery/AGENTS.md), and the import contracts cover them. Their code isn't in this snapshot. The design page has the design.
  • Route B training. We've built and tested the pure dataset derivation (routeb/dataset.py, routeb/signal_texts.py). Training, serving and evaluating the adapter aren't in this snapshot.
  • Act 2 scored runs. None has run. We've recorded the task pool and the gold check, and the first calibration runs are incomplete. A scored run needs a frozen pre-registration that fixes the warning budget, precision at the budget and net benefit.
  • Act 1 scored episodes. We've built and tested the episode runner, the text description, the strict strategy parser and the navigation. The day-one probe parsed 40 of 40 model replies at about 11 s per decision, and 12 of 40 observations read "nothing notable" before we added layout text. No scored episode is recorded in results/. measured
  • The live warning budget. It's built and tested in the core, and no live harness has exercised it yet.
  • Readers. One reader, OpenHands. A reader for another harness is one file by design, and none is in this snapshot.

Words used here

pain point
A moment in the history that went wrong: a failed command, a reworked edit, a loop, a correction, a review flag, a change made without checking what depends on it.
harness
The coding-agent tool (OpenHands, mini-SWE-agent, Muse Code and so on). ai-symbiont doesn't build one; it reads their logs and feeds them notes.
MCP
Model Context Protocol: how a model calls a tool. Here there is one tool, recall, taking one plain question.
hook
A script a harness runs at an event (session start, a new prompt, after a tool call). The push side of delivery.
LoRA
A small set of extra weights trained on top of a model. Route B trains one per developer on Muse Glimmer.
balanced accuracy
The average of the true-positive rate and the true-negative rate; 0.5 for a learner that never flags. established
precision
Of the warnings given, the share that were followed by a pain point.
warning budget
The share of steps a learner may warn on, fixed on training data.
floor / reference / under test
The role of a result row: the worst reasonable thing, the plain baseline, the thing being judged.
Kenyon cell
A neuron of the fly's mushroom body. The learner uses the published count and a local learning rule, with random wiring unless the user supplies the real one.
