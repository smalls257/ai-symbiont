Design · Meta Global AI Developer Hackathon (indie, solo) · draft 2026-10-27 · build window Oct 27 – Nov 4
Frontier models serve everyone. A small personal learner, trained on your own agent history, makes one yours.
It sits beside a coding model, learns the mistakes you and your agent keep making, and warns the agent before it makes them again. It runs on your machine, and works with API models and with open weights.

1

Why this, and for whom

A pathway from a general model to one tailored to one person, without a training cluster.

▶
  • For: company teams that already have agent-session history, and solo devs with one machine.
  • Tailored per person from their own past sessions, not per company.
  • Why small: one ~5k-cell learner per developer is cheap enough to give everyone their own and keep learning. Fine-tuning a big model per person isn't. hypothesis
  • Design principle: small networks are good at deciding (what to fetch, is this going badly) and bad at storing compressed memories. So we keep the original text and let the network pick from it.
Goals, non-goals, anti-goals
GoalsOne install, then warnings appear inline in chat · real runs proving fewer repeated mistakes · works across harnesses · honest baseline beside every result · Freedoom as the visual hook
Non-goalsMaking the model smarter at tasks it can't do · compressed memory · a GUI · building our own harness · the sidecar acting on its own
Anti-goalsclaiming that the real fly wiring improves results · branding it "Doom" · hiding a fly that only ties simple counters · sending private data to a tier that may train models · any claim about how fast it learns

What we build

One miner feeding two routes: notes in context for any model, or a personal adapter in the weights for open models.

▶
MinerReads your history and finds pain points. Rule-based, CPU, no AI model.
Route A · any modelA small swappable learner (fly mushroom body first) flags trouble and picks what to recall; MCP + hooks put notes in chat. The model decides.
Route B · open weightsA personal LoRA on Glimmer learns the same points, recalls them, and makes the correction itself.
What the developer sees
  1. Run symbiont setup: a guided terminal wizard.
  2. It finds your history and lists projects with session, PR and correction counts. Pick all, or a mix.
  3. Preview the top pain points it found, with the original text.
  4. It trains the fly network on CPU (and optionally a LoRA adapter on a GPU, for open-weight models), then installs into your harness.
  5. Code as usual. Notes appear when relevant:
you › add retry to the webhook handler
⚠ symbiont · last 2 edits to webhooks/handler.py broke tests/billing
agent › editing webhooks/handler.py …
↺ symbiont · recalled: you rejected exponential backoff here on Oct 12 ("use the queue's retry")

History never leaves the machine. If a log can't be read, the wizard names it and asks; it never quietly trains on less.

Miner: what counts as a pain point
  • A command that failed · an edit later reworked · code a PR reviewer flagged · a place you corrected the agent · a loop (same command, same file re-read) · blast radius (a change made without checking what else it affects).
  • One reader per harness, one shared record format. First readers: OpenHands, Claude Code, mini-SWE-agent, Muse Code. Codex and Cursor later.
The learner: a swappable slot (fly mushroom body first)
  • Swappable. The learner is a slot any small home-grown network can fill. Plain counters and similarity search sit in the same slot as references. Whichever wins on offline numbers by ~Oct 30 runs live; if the network only ties, we say so.
  • 86 inputs fan out to 5,177 Kenyon cells, using the fruit fly's published numbers; the top 5% fire; a readout learns with a local dopamine-like rule, no backprop. established
  • Random wiring by default. The real FlyWire wiring is an optional download. We say "a learner built on the fly's circuit", and make no claim that the real wiring improves results.
  • Always compared against plain counters. Simple counting is often hard to beat. hypothesis
  • Shown live: sparse cells lighting up, a dopamine pulse when it learns.
Delivery: how notes reach the model
  • Hooks push short notes at session start, on each prompt, before model calls and after tool calls (event names per a third-party guide; inline display still to be tested).
  • MCP recall lets the model ask for memories itself.
  • The model decides. We don't build a harness and the sidecar never acts on its own. If models ignore notes, the fallback is a louder note (placed in the tool result, worded as a finding).
  • Installs into Muse Code and Claude Code. Glimmer in mini-SWE-agent gets the same notes through a thin wrapper.
Route B: the personal LoRA on Glimmer
  • Same points as Route A, learned into the weights instead of delivered as notes.
  • Recall: trained on self-study Q&A about each pain point, so it can answer "what broke last time I touched X?".
  • Correct: because we own the model, it doesn't stop at a warning. It's trained on situation → corrected action: what you did after correcting the agent, the edit version that survived, the command that finally worked, the files a change should have checked.
  • Risk: one adapter holding a lot of history may forget most of it. Mitigation: keep each person's set to their top pain points; per-chunk adapters with a picker as fallback. hypothesis
  • Cost: ~16 h of GPU per 2,000 training steps (projected), so one or two adapters overnight. Serving the adapter alongside the existing model server is checked on day 1. hypothesis
  • Lab only: direct vector injection (~3 tok/s), and one per-chunk adapter experiment.

How we prove it

Real models on real bugs, with and without the fly. Freedoom as the visual hook.

▶
  • Act 2, the claim: a "developer's week" of real bugs from one open-source repo, graded by its own tests. Plain model vs Route A (notes), Route B (personal LoRA) and both.
  • Main number: how often the agent repeats a mistake. Second: tests passing.
  • Act 1, the hook: a Muse model plays Freedoom (via ViZDoom) from a text description of the game; the fly flags loops and wasted moves.

Compared only within a model. Tasks are calibrated so each model solves them only sometimes (~20–60%): the fly prevents repeated mistakes, it doesn't add skill. [hypothesis]

Fairness rules
  • History the fly learns from never includes past runs of the tasks being scored (no peeking at answers).
  • The fly keeps learning between sessions during the week; both arms are graded against the same reference history.
  • Each scored run has a written plan frozen in advance; amendments are dated.
  • The counters baseline is shown next to the fly everywhere.
Day 1–2 go / no-go checks
  • Freedoom + ViZDoom + Glimmer: one full episode.
  • Glimmer task calibration on the candidate repo.
  • Does Muse change its next action when warned? unmeasured
  • Do Muse Code's hooks show text inline in chat?
  • Docker runs the repo's test images on the desktop.
Act 1: Freedoom details
  • The game pauses each step while the model thinks; the video is sped up. Freedoom levels or ViZDoom scenarios only.
  • The model picks the strategy ("get the blue key, back to the blue door"); simple scripted moves carry it out, labeled as such.
  • Both scored and showcase: fixed levels and seeds, all runs reported; the video clip is cut from those runs and labeled "selected episode", with the full scoreboard under it.
  • Muse Spark plays the scored episodes; Glimmer plays a few for the open-weights angle.

Guardrails

Licenses, data handling, budget and hardware: the rules every part follows.

▶
Data

The scored repo + its past agent runsnebius SWE-rebench OpenHands trajectories; sqlglot leads (alternatives under review)CC-BY-4.0 established
Real human corrections (miner demo)SWE-chat (gated)ODC-BY · stays local
PR review signals (optional)AIDevCC-BY-4.0 · counts and labels only

Raw data is never committed; it downloads on setup. Real people's text is never sent to a model tier that may train on it.

Licenses and naming
  • ViZDoom is a dependency, never vendored. Freedoom is BSD-3, downloaded on setup.
  • "Doom" is a trademark: we say "plays Freedoom via ViZDoom".
  • FlyWire connectome data is never committed; an optional user download, cited as requested.
  • Muse Glimmer is Apache 2.0, so adapters are fine.
Budget and hardware
  • $150 API credit; every paid run is estimated up front and approved first. Rough guess: $0.05–0.10 per Spark task run. hypothesis
  • One home GPU box runs Glimmer by day and training / art overnight, one job at a time.
  • A desktop runs the task and test containers. The laptop only orchestrates.
Hackathon rules
  • Public repo with only work done during the event; everything built fresh.
  • 3-minute video. Judging: Impact 30 · Meta tooling 25 · Technical depth 20 · Demo 25.
  • Bonus targets: Best Build on Meta Open Weight Models, Best Agentic Use-Case.
