Design · Meta Global AI Developer Hackathon (indie, solo) · draft 2026-10-27 · build window Oct 27 – Nov 4
Frontier models serve everyone. A small personal learner, trained on your own agent history, makes one yours.
It sits beside your coding model and learns the mistakes you and your agent keep making. Then it warns the agent before the next one. It runs on your machine, with an API model or with open weights.

1

Why this, and for whom

A path from a general model to one tuned to one person, with no training cluster.

▶
  • Who it's for: company teams that already hold agent-session history, and solo developers with one machine.
  • Tuned per person, from their own past sessions, not one learner per company.
  • Why small: one learner of about 5k cells per developer is cheap enough that everyone gets their own, and it keeps learning. Fine-tuning a big model per person isn't. hypothesis
  • The design principle: small networks are good at deciding (what to fetch, is this going badly) and bad at storing compressed memories. So we keep the original text and let the network pick from it.
Goals, non-goals, anti-goals
GoalsOne install, then warnings appear inline in chat · real runs proving fewer repeated mistakes · works across harnesses · honest baseline beside every result · Freedoom as the visual hook
Non-goalsMaking the model smarter at tasks it can't do · compressed memory · a GUI · building our own harness · the sidecar acting on its own
Anti-goalsclaiming that the real fly wiring improves results · branding it "Doom" · hiding a fly that only ties simple counters · sending private data to a tier that may train models · any claim about how fast it learns

What we build

One miner feeds two routes: notes in the chat for any model, or a personal adapter in the weights of an open model.

▶
MinerIt reads your history and finds the pain points. It's rule-based, runs on CPU and uses no AI model.
Route A · any modelA small learner, swappable, flags trouble and picks what to recall. The first one is built on the fly's mushroom body. MCP and hooks put the notes in chat, and the model decides what to do with them.
Route B · open weightsA personal LoRA on Glimmer learns the same points, recalls them, and makes the correction itself.
What the developer sees
  1. You run symbiont setup, a guided terminal wizard.
  2. It finds your history and lists your projects with session, PR and correction counts. You pick all of them, or a mix.
  3. You preview the top pain points it found, with the original text.
  4. It trains the fly network on CPU, and a LoRA adapter on a GPU if you want one for an open-weight model. Then it installs into your harness.
  5. You code as usual, and notes appear when they're relevant:
you › add retry to the webhook handler
⚠ symbiont · last 2 edits to webhooks/handler.py broke tests/billing
agent › editing webhooks/handler.py …
↺ symbiont · recalled: you rejected exponential backoff here on Oct 12 ("use the queue's retry")

Your history never leaves the machine. If the wizard can't read a log, it names the file and asks you. It never quietly trains on less.

Miner: what counts as a pain point
  • A command that failed · an edit later reworked · code a PR reviewer flagged · a place you corrected the agent · a loop (same command, same file re-read) · blast radius (a change made without checking what else it affects).
  • Each harness gets one reader, and every reader writes one shared record format. The first readers are OpenHands, Claude Code, mini-SWE-agent and Muse Code. Codex and Cursor come later.
The learner: a swappable slot (fly mushroom body first)
  • Swappable. The learner is a slot that any small home-grown network can fill. Plain counters and similarity search sit in the same slot as references. Whichever wins on the offline numbers by about October 30 runs live, and if the network only ties, we say so.
  • 86 inputs fan out to 5,177 Kenyon cells, the fruit fly's published numbers. The top 5% fire, and a readout learns with a local dopamine-like rule, with no backprop. established
  • The wiring is random by default, and the real FlyWire wiring is an optional download. We say "a learner built on the fly's circuit", and we don't claim the real wiring improves results.
  • We always compare it against plain counters, because simple counting is often hard to beat. hypothesis
  • You'll see it live: sparse cells lighting up, and a dopamine pulse when it learns.
Delivery: how notes reach the model
  • Hooks push short notes at session start, on each prompt, before model calls and after tool calls. The event names come from a third-party guide, and we haven't tested inline display yet.
  • MCP recall lets the model ask for memories itself.
  • The model decides. We don't build a harness, and the sidecar never acts on its own. If models ignore the notes, we fall back to a louder note, placed in the tool result and worded as a finding.
  • It installs into Muse Code and Claude Code. Glimmer in mini-SWE-agent gets the same notes through a thin wrapper.
Route B: the personal LoRA on Glimmer
  • The same points as Route A, learned into the weights instead of delivered as notes.
  • Recall: we train it on self-study Q&A about each pain point, so it can answer "what broke last time I touched X?".
  • Correct: we own the model, so it doesn't stop at a warning. We train it on situation → corrected action: what you did after correcting the agent, the edit that survived, the command that finally worked, and the files a change should have checked.
  • Risk: one adapter holding a lot of history may forget most of it. So we keep each person's set to their top pain points, and we fall back to per-chunk adapters with a picker. hypothesis
  • Cost: about 16 h of GPU per 2,000 training steps, projected, so one or two adapters overnight. On day 1 we check that the adapter serves beside the existing model server. hypothesis
  • Lab only: direct vector injection (about 3 tok/s), and one per-chunk adapter experiment.

How we prove it

Real models on real bugs, with and without the fly, and Freedoom as the visual hook.

▶
  • Act 2 carries the claim: a "developer's week" of real bugs from one open-source repo, graded by its own tests. We run the plain model against Route A (notes), Route B (the personal LoRA) and both together.
  • The main number is how often the agent repeats a mistake. The second is how often the tests pass.
  • Act 1 is the hook: a Muse model plays Freedoom via ViZDoom from a text description of the game, and the fly flags loops and wasted moves.

We compare arms only within one model. We calibrate the tasks so each model solves them only sometimes (about 20–60%), because the fly prevents repeated mistakes and doesn't add skill. [hypothesis]

Fairness rules
  • The history the fly learns from never includes past runs of the tasks we score, so it can't peek at the answers.
  • The fly keeps learning between sessions through the week, and we grade both arms against the same reference history.
  • Each scored run has a written plan we freeze in advance, and every amendment carries a date.
  • The counters baseline sits next to the fly everywhere.
Day 1–2 go / no-go checks
  • Freedoom + ViZDoom + Glimmer: one full episode.
  • Glimmer task calibration on the candidate repo.
  • Does Muse change its next action when warned? unmeasured
  • Do Muse Code's hooks show text inline in chat?
  • Docker runs the repo's test images on the desktop.
Act 1: Freedoom details
  • The game pauses at each step while the model thinks, so we speed the video up. We use Freedoom levels or ViZDoom scenarios only.
  • The model picks the strategy ("get the blue key, back to the blue door"), and simple scripted moves carry it out, labeled as scripted.
  • Scored and showcase at once: fixed levels and seeds, and every run reported. We cut the video clip from those runs, label it "selected episode", and put the full scoreboard under it.
  • Muse Spark plays the scored episodes, and Glimmer plays a few for the open-weights angle.

We never commit raw data; it downloads on setup. We never send real people's text to a model tier that may train on it.

Licenses and naming
  • ViZDoom is a dependency, never vendored. Freedoom is BSD-3, downloaded on setup.
  • "Doom" is a trademark: we say "plays Freedoom via ViZDoom".
  • We never commit FlyWire connectome data. It's an optional download for the user, cited the way FlyWire asks.
  • Muse Glimmer is Apache 2.0, so adapters are fine.
Budget and hardware
  • We have $150 of API credit. We estimate every paid run up front, and the owner approves it first. Our rough guess is $0.05–0.10 per Spark task run. hypothesis
  • One home GPU box runs Glimmer by day and training / art overnight, one job at a time.
  • A desktop runs the task and test containers. The laptop only orchestrates.
Hackathon rules
  • The repo is public and holds only work done during the event. We built everything fresh.
  • 3-minute video. Judging: Impact 30 · Meta tooling 25 · Technical depth 20 · Demo 25.
  • Bonus targets: Best Build on Meta Open Weight Models, Best Agentic Use-Case.
