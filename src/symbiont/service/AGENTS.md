# service: the localhost service and its event log

See root CLAUDE.md for the repo rules. This file covers `src/symbiont/service/`.

**Purpose.** HTTP on localhost: `/observe` returns notes, `/recall` answers one question from stored lessons, `/learn` registers a harness log (`reader`, `session_log_path`, `project`), re-mines the project from all its logs and updates the decider. `events.py` writes the event log.

**Violation prevented: Black Box.** Failure must be visible from outside, so every call appends a timestamped event (kind, project, latency, outcome) that the dashboard replays. A spark-bound recall that would return a private record answers 409 with "private history withheld from Spark" rather than an empty answer.

## Invariants
- Route A (`--warner`, `--memory-url`, `--memory-dir`): the logistic warner decides per step, option A (`core/note_rules`: boundary steps, 2 notes per session, none in the 5 steps after one) rations, and the loopback memory model (`memory_model.py`, `Endpoint.LOCAL_MEMORY_MODEL`) writes the one line. An unusable reply answers 503, which the hook shows as "symbiont offline". Only projects named in the adapter's manifests are answered by the model; the event log carries prompt and note sizes and milliseconds, never the prompt.
- Mining is a tracked job (`mine_route.py`, `mining_jobs.py`; Violation prevented: Black Box). `POST /mine` {project, sources: [[reader, path]]} starts it in the background for an allowed repository (400 otherwise) and answers at once; `GET /mining/<project>/progress` (and `POST /mine/progress` for clients that can only POST) answers {state: running|done|failed, sessions_read, sessions_total, pain_points, fixes_paired, lessons, recent: [short titles], error}. The job reads and mines without the service lock, takes it only to save, stores nothing when it fails, and its end is an event. While a project's job runs, failed, or found nothing, `GET /dashboard?project=` serves the Mine stage alone (`static/mining.js`, driven by `{"mining": ...}` in the page's one data object), so a dashboard opened early never shows an empty view; when the job is done with lessons the page reloads into the pain-point view. The service never opens a browser; the CLI does (delivery side).
- The Pain points stage (`#s1`) is one selection (a theme, a pattern, or both) scoping every panel (`static/struggle.js`). `struggle_view.py` only assembles what mining stored (`store.mined.session_facts` and `session_strips`) into `stage` in the page's data object; a store mined before session facts existed gets `stage: null` and the page says to mine again, never an empty chart. Strip labels and task labels leave through `scrub`. Every value reachable by hover is also reachable by keyboard focus. Add every new static file to `FILES` in `dashboard_page.py` (a test fetches each script the page names).
- PR lessons may carry `quote` and `quote_role` (`pr_learning.checked_quote`): the reviewer's exact words, at most 300 characters. The service never sees the review text, so the quote is model-supplied and NOT checked against the comment; it refuses a quote with no PR link, a handle or address, a credential, an unknown role or an over-cap quote, with a message, and stores nothing.
- `/recall` accepts exactly the plain-question payload; extra fields are rejected with 400.
- `curation_routes.py` serves the routes the session's model calls (`lessons/add`, `corrections/*`, `reviews/*`, `focus`); `onboarding.py` holds what first sessions say; `dashboard_page.py`/`dashboard_view.py` and `static/` serve `GET /dashboard`. symbiont makes no model calls; history is shown only to a session of the same harness unless `cross_harness` is on.
- `reflection.py` serves `/reflect`: at session end it asks the session's own model for non-obvious lessons, once per session (guard kept in `reflections.json`, survives restarts), only for an allowed repository and only at a milestone (an edit, then a later check that passed and changed nothing, `miner/changes.passed_check`), because Stop fires every turn in an interactive session; every refusal carries `why_not`. Each `/reflect` call and each `/reflect/finished` (the reflection turn's own Stop) is an event with `reflection`: asked or why not, and how many lessons the turn saved (0 = the model read the question and ended its turn without answering; null = the service restarted in between). Lessons arrive through `symbiont_add_lessons` labeled `from reflection`; symbiont makes no model call.
- `ignore_route.py` serves `POST /lessons/<id>/ignore` {project}, `POST /ignored/restore` {project, signal, key} and `GET /ignored?project=`: the same consent gate as the curation routes, an unknown lesson id is a 400 naming it. The page's data carries `ignored` (label, signal, key) for the collapsed Ignored group (`static/ignored.js`).
- `/lessons/<id>/context` stores the developer's words (`context_route.py`); a note never fires on a passing tool result; in plugin mode (a repo registry is wired) a note needs a stored lesson with the same normalized failure signature (`core/failure_signature.py`).
- `repo_gate.py` answers per repository (`store/repos.py`): a repository that is not allowed is not observed and writes no event; never-asked gets one onboarding note in `announce` at SessionStart; muted kinds of trouble stay silent; the exact-repeat rule (`core/repeat.py`) speaks once per lesson per session. The gate also says the developer's corrections once per session as one "House rules for this repo (from your corrections and PR reviews)" note at the first prompt (a PR-linked rule counts as a correction; own corrections first, then PR rulings), and a rule pinned to a file once when a successful read or edit names that file (`file_scoped_rules`: the lesson's own file only, never words or areas) (it takes one of the `MAX_RULE_NOTES` slots; `fired_by` is `rule: house rules (<ids>)`), and never says a written lesson that a later correction supersedes (`core/house_rules.py`); each such lesson that matched the work is an event with `superseded` (lesson, by, excerpts) which `symbiont why` shows (`supersessions.py`). `/status` reports the answer, lesson count, muted kinds and nightly state. Events carry the project so `symbiont why` can find the last note. A rule note's `fired_by` names each signal with its weight (for example `rule: tag: non_database_attrs (+3); words: sqlite (+1)`); see `core/rule_relevance.py`. `operator_commands.py` is the `/symbiont` command set (`repo`, `status`, `why`, `mute`, `forget`, `lessons`); `cli.py` injects the data directory and how to ask the running service, so nothing here imports a client.
- An empty store answers "no history for this project yet", never a fake note.
- No raw history: notes and recall answers come from lessons (what happened, how it was resolved, the check to run); `/observe` has no stored records to recall from.
- A Spark-bound note must rest only on lessons the Spark view returned (under the user's own-history consent, read from `consent.json` at start); anything else answers 409.
- A Spark-bound call may use the memory model only when its adapter's recorded provenance (`adapter.json`, written by `train_memory.py` after a successful run) is `public`, or `own_history_with_consent` while consent is still given; `personal` or a missing record answers 409. Spark-bound answers and notes are scrubbed of credentials. Consent is read once at start: a withdrawal (`symbiont consent withdraw`) applies when the service restarts, not before.
- State between sessions is the decider state, saved and restored; no shared mutable state across workers.
- `symbiont nightly` (`nightly_command.py`) trains the repository's judge locally: `nightly_rows.py` (pure: plug round 4's nightly rows from the store's lessons), `nightly_kit.py` (the fixed general-judge base and replay files; a missing piece raises), `nightly_setup.py` (`symbiont nightly setup`: checks the user's Llama 3.2 1B Instruct folder and the downloaded kit files against pinned SHA-256s, merges the two adapters locally; no network call, so no egress change; Violation prevented: Silent Fallback, a wrong base would train a different judge), `nightly_backend.py` (mlx on Apple Silicon, torch on CUDA, otherwise `NoTrainingHardwareError`, never the CPU), `nightly_run.py` (stages with timings; the record is written only after the trainer exited 0), `nightly_peft.py` (mlx adapter to PEFT bytes), `nightly_locate.py` (with no `--base`/`--kit-files` and no built kit, finds the Llama folder and the nightly kit: `~/.symbiont/models/...`, then the newest Hugging Face cache snapshot under `$HF_HOME/hub` or `~/.cache/huggingface/hub`; pure over `SearchRoots`; nothing found raises `ModelsNotFoundError` with the `hf download` commands, never a download; Violation prevented: Silent Fallback), `nightly_fetch.py` (when nothing is found, the detached job's first phase downloads the base and kit into `<data dir>/models` through `symbiont.egress.download_file`; the job file is `downloading` with bytes done and total, which `symbiont status` shows; a failure names host and path; Violation prevented: Black Box), `nightly_tools.py` (processes, hardware probe, the loopback judge call), `nightly_bundle.py` (where the trainer, merge and judge-server scripts are: `$SYMBIONT_ROUTEA_DIR`, else a checkout's `scripts/routea`, else the copy that ships in the package as `routea_bundle/*.script` and unpacks to `~/.symbiont/routea` as `.py`; the `.script` suffix is deliberate, those files import torch and serve a socket, which the `.py` gates forbid under `src/`; `tests/service/test_nightly_bundle.py` fails when a copy drifts from `scripts/routea`, and the fix is the `cp` it prints), `nightly_background.py` + `nightly_job.py` (`symbiont nightly start`: checks the kit, lessons, hardware and packages in the foreground, launches `nightly work` detached and follows its `job.json` for at most 45 s; `work` always leaves done or failed; `symbiont status` reads the file; Violation prevented: Black Box, a training that outlives its tool call), the `nightly` extra of `pyproject.toml` (mlx-lm on Apple Silicon, torch, peft, transformers; a missing package says `uv tool install 'ai-symbiont[nightly] @ git+...'`, Violation prevented: Silent Fallback), `nightly_schedule.py` (`Platform` StrEnum: launchd, crontab, schtasks; pure generators, a `SchedulerSystem` the tests fake). Violation prevented: Silent Fallback (a failed night keeps the older adapter and record; a stale record reads stale). Exit codes: 0 trained, 1 failed, 2 no lessons. The checker is on by default (Violation prevented: Silent Fallback): the service always reads `<data-dir>/nightly` (`--nightly-dir` only moves it); a repository with a valid record is answered by the agree rule with that repository's judge, with no flag; one without a record keeps the plain ranker and `status` says "checker not trained yet". The record carries `judge_start` (`judge_start.py`: python, base, adapter, device, port) so `nightly_tools.ensured_judge` starts or reloads the judge server at the end of a night and `agreed_recall.py` starts it once, non-blocking and loudly, when a recall finds it down; the recall itself answers 503 "symbiont checker offline" (never the ranker alone), and a stale record is retrained, not started. A shown note's event carries `checked_by` (checker, rule, verdict, lessons, trained_at; never a score) which `symbiont why` and the dashboard header (`last_checked`) read. The agree rule also gates the hook-time exact-repeat recall (`AgreedRecall.vet`, called by `/observe`; Violation prevented: Silent Fallback, a trained repository never shows an unchecked recall): the situation is built from the failed record (`core/judge_format.failure_situation`), the judge gets `HOOK_BUDGET_S` (0.35 s, under the hook's 0.6 s), a no is a held note, a down judge answers 503 "symbiont checker offline" and is restarted, a slow one 503 "symbiont checker slow" (not restarted), and the once-per-session mark is withdrawn so the repeat is checked again. House and file rules (`why` starts with `rule`) and repositories with no record are never gated. `NightlyJudges.report` is the one reader of the state (`never`, `trained`, `stale`) that `/status`, `symbiont status` and the dashboard header show.
- Periphery: sockets, files and the clock live here and in tests marked `periphery`.
