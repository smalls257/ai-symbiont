# Core v3: Glimmer trained on its own solved runs (self-distillation)

**FROZEN 2026-10-31**, committed before the full training and before any v3 test run. After the freeze, only a dated amendment may change anything, and an amendment cannot change the data, test tasks, arms, measures or decision rule. The planned amendment adds the adapter's GGUF hash after training, before the first test run.

Claim tags: [measured] = observed in our own run; [established] = known by construction or from the literature; [hypothesis] = a guess this run can support or refute.

## Question

Does plain Glimmer solve more issues of a repository after a LoRA trained on its own earlier solved runs there (kept in its own format, thinking in the thinking slot) than plain Glimmer does? No speed-of-learning words [established].

## Training data (fixed at collection time, 2026-10-31 16:53 PDT) [measured]

- **Source.** Solved runs of plain-equivalent arms: Plug-in-the-loop's two arms (plug never spoke, so both are plain Glimmer), D2's plain arm and v2's plain arm, on the runs recorded by the collection time. Runs that were in flight at the time are excluded; later runs never enter training.
- **Scope.** Non-Django tasks only, because Django trajectories of different arms share one file name and cannot be attributed.
- **Size.** 20 train tasks (sqlglot 13, PennyLane 7) and 32 solved runs, at most 2 per task. The manifest's sha256 is `f3a1d3dfd9960237ef413e0cd92f32527e813f5a73b8d252357545956aeb6ca2`.
- **Rows.** Windows of up to 3,500 tokens: the system and task turns, then a few turns around each of the last three edits and the final submit. Glimmer's own reasoning stays in the thinking slot. Loss is on assistant turns only (reasoning and action), never on observations. The builder is `scripts/routeb/core3_self_rows.py`. It gives **95 rows, 264,692 tokens, 53,282 trained tokens** from 18 tasks. The row file's sha256 is `3988e42b762197facd9a5cf26fdc9fe572f96a7e5bdc1a6e1786f3176fedbbbd`. The trained-token count is below the 150-250k goal because only 32 solved runs exist; it is not padded [measured].
- **Row facts** [measured]. Reasoning is 34% of the assistant tokens in these rows (5% in the v2 rows from Spark sessions), and the median reasoning per step is 55.5 characters, against 58 for v2-A and 54 for v2-C.
- **Training.** The same LoRA recipe as v2 (rank 64, 1 epoch, batch 1, 16k window) on the Strix; one adapter, `Muse-Glimmer-30B-v3-self`.

## Pilot (exploratory, no claim)

A 15-row smoke training (`v3-smoke`) and a greedy generation check on 3 train-task prompts, plain against smoke. It touches no test task. The full training starts only if the pipeline works and the smoke model's median reasoning length is at least half of plain's [established].

## Test tasks (fixed now, before training)

- **40 tasks** (sqlglot 28, PennyLane 12): non-Django tasks of the same two repositories that had no Glimmer run at the collection time, listed in `v3-test.json` (`results/core-v3-test-set.json`, sha256 `88aeaf48e7cc6f8f6754678a002470af143eb32bd2ba094095469fb27bbcf884`). 6 are D2 test tasks never run; 34 are later candidates outside D2's 100, chosen in the order of sha256(`core3-test:<id>`). No test task appears in training: the collector asserts it [established].
- A test task may also receive Plug-in-the-loop runs later; that is not leakage, because the training data was fixed first [established].

## Arms and runs

- **P** (plain Glimmer, the `plain64` router preset) and **V3** (`Muse-Glimmer-30B-v3-self`), 2 runs each per task, back to back in one block on the Strix router, tasks in the order of sha256(`core-d2-order:<id>`). Containers run on the 5080. 64k context per request, temperature 0.6, step cap 75, wall cap 45 minutes. Seed: first 8 hex digits of sha256(`core3-v3:<instance_id>:<arm>:<run>`) for both arms [established].
- Voids, drops and the adapter probe follow D2's rules. **Cutoff** 2026-11-01 18:00 PST (UTC-8); no new task starts after it. The analysis uses tasks where all four runs are graded [established].

## Primary and secondary

- **Primary: solve rate, V3 minus P, paired by task** (each task's mean of its two runs), mean over analyzed tasks with a 95% percentile bootstrap interval (10,000 resamples, seed 20261101). **Verdict words:** "V3 solves more" only if the lower bound is above 0; "V3 solves fewer" only if the upper bound is below 0; otherwise "no detected difference" [established].
- **Secondary (descriptive):** the code-level pain points (reworked edits, loops, blast radius, failed commands beside) per run, V3 minus P, with the same interval; steps used; reasoning length per step [established].
- **Size, said plainly.** With at most 40 tasks the smallest detectable gain is large, about 20 points or more at a plain rate near 0.4; a smaller effect will read as "no detected difference" [established].
