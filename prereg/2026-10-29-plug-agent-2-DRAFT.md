## Question and the claims it supports

1. **Forced delivery (primary, scored).** At the point just before a coding agent makes a mistake that an earlier session's stored, applicable lesson describes, does showing that lesson's note, verbatim, make it less likely to make that mistake than showing nothing? The note is always the correct, pre-labeled lesson; the judge is not involved. **Oracle-timing caveat:** the note is placed at a moment chosen because the source run made that mistake next; Plug cannot know when a mistake is coming, so this measures what a note does when it is shown at the right time, not what a note-giving system achieves.
2. **No end-to-end figure in the pilot.** The derived product of forced-delivery prevention and Plug's coverage is dropped: 11 points in 2 distinct (repository, key) pairs, all generic environment errors, do not generalize to the situations round 3's coverage was measured on [established].
3. **Judge-gated direct arm: NOT RUN.** Declared before the freeze: at the measured capacity (about 60 own points; the judge needs a host that does not take the desktop GPU, and its CPU run took 142 to 206 s per call under Core's load) the arm cannot reach the 150-point, 50-speaking-points threshold, and the primary and derived figures do not need it. No judge-gated, `rag` or `ranker` branch is run. [measured]

## Design: branch points

- **Branch point.** The first moment in a run at which the agent executes a command that fails with a known key (key rule below). All arms continue from the same state: the same container filesystem and the same message history.
- **One snapshot method: replay, then `docker commit`, at the state just before the erroring command.** For both sources the recorded commands before the assistant turn that issued the erroring command are executed in order in a scrubbed container, so their side effects exist exactly as in the source run; the container is then committed. **Fidelity probe (frozen):** every replayed command must return its recorded return code and, if it failed, the same normalized error line, else the point is void and listed (a hash of the source run's own state is not reconstructable, so the replayed outputs are the check). The SHA-256 of `git diff HEAD`, `git status --porcelain` and the sorted hashes of untracked files is taken before the commit and again in every branch container before its first step; a mismatch voids the point. A void point is never run anyway [established, by construction]. **Scope of the hash [established]:** it covers only `/testbed`'s tracked and non-ignored files, not `site-packages` or other system state; the per-command replay check is the real probe of fidelity.
- **History replay is byte-identical:** each branch starts from a deep copy of the message list up to, and **excluding**, the assistant turn that issued the erroring command. The forced arm's note is appended under the last message of that history, so the agent has it in view before it chooses its next command; `none` appends nothing. The recorded reasoning text stays in the history objects as the model returned them; what the server renders from them is the same function of the history in every arm [established].
- **Sampling.** Temperature 0.6 with no seed, for the prefix and the branches alike, so the B branches of an arm are independent samples [hypothesis]. (PLUG-AGENT-1's temperature 0 would make every branch of an arm identical.) Reasoning low, 4,096 tokens per reply, step limit 75, wall cap 45 min.
- **Sources of branch points (pooled for the primary; reversal of the earlier "drop Core sources" ruling, by the owner).** (a) **Own** `none` prefix runs on the pool's labeled tasks, on the laptop or the desktop Glimmer. (b) **Core** plain-Glimmer runs on the Strix (same GGUF sha256), used as *sources of state only*: their outcomes are never used and never scored for Core. For (b), no container survives, so the driver **replays** the recorded commands in a scrubbed container, requires the erroring command to return the recorded return code and the same normalized error line (otherwise the point is void and listed), and then commits the container, the same snapshot method as (a). Eligibility of a Core run: its recorded step limit (75), wall cap (2,700 s) and prompt templates (hash `8259e67f`) equal this test's [measured: all 152 trajectories do]. Its sampling was the server default, not 0.6; this is declared and reported per source. **Selection rule of (b):** Core's screening kept tasks by its own bands, so these tasks are enriched for mistakes; the report says so. **Django (66 tasks) is excluded**: its tasks are SWE-bench ids with a different environment and grader that this harness does not run. [established]
- **Lessons for the Core source** come from the same template builder (`lessons_in_session`) applied to Core's **earlier** plain runs of the same repository: only runs on tasks created strictly before the branch task, never the branch task's own run; the label (frozen prompt) is applied to those lessons. The lesson source differs from the pool's (an agent's own earlier mistakes against nebius OpenHands sessions) and is disclosed. The local-run reader's allowlist was widened to the five public SWE-rebench repositories of these runs (commit 0726217).
- **Pooling.** The primary pools own and Core points (the unit is the point). Per-source estimates are reported as secondaries. **Divergence flag:** if the BCa interval of the difference between the two sources' means excludes zero, the pooled figure is reported as "divergent sources" and stays the primary only with that label [established, declared now].
- **Arms at each branch point** [established]. `none` (nothing added) and `forced` (the correct lesson's note appended verbatim under it). The correct lesson is the `applies`-labeled lesson whose key equals the failing key (the lowest lesson id if several). After the branch point every arm is silent: a branch differs from another only by the note at the point. **Branch order:** the B none and forced branches of a point alternate by index (none, forced, none, forced, ...) so a drift of the server over the point's hours falls on both arms.
- **Branches per arm per point: B = 6** (Sizing), each a continuation of **W = 15 model calls**. A branch ends at W calls, at a submit, at three format errors in a row, at the step limit or at the wall cap, whichever comes first. **The wall cap (45 min per run or branch) is enforced by the agent's own limit and ends the branch like any exit** (tested in the harness: `TimeExceeded` is an interrupt that adds the exit message). **Early exits are not replaced:** a branch that ends early has its repeats counted up to its end and is kept; the exit status rates are reported per arm [established].
- **No `none2` arm.** The within-arm spread of the B branches at each point is the noise floor.

## Frozen rules carried over from PLUG-AGENT-1 [established]

- **Voids.** A branch lost to an infra or model_api error is requeued once. If a branch of either primary arm (`none`, `forced`) is lost twice, **the whole point is void** and listed with its reason; voids are reported per arm (the void record names the arm and branch index). Reaching the wall cap is not a void.
- Full config pinning: `results/plug-agent-2-config.json`. **The runner checks, before any run:** the whole config file's sha256 (given on its command line from this prereg's frozen header), the label file, label prompt, mistake-rule file and pool summary hashes it pins, and the served model (alias, byte size and parameter count of the pinned GGUF, read from the server's `/models`). The GGUF file's own sha256 is checked where the file lives, at server start, by the owner's launcher; the judge's `selection.json` and adapter hashes stay in the config as the provenance of round 3's coverage c. The config holds the GGUF sha256 and llama-server versions of both servers, temperature, W, B, limits, thresholds, `selection.json` and adapter hashes, the pool summary hash, the requeue cap, the Spark labeling cap, **the cutoff time (2026-11-01 06:00 PT) and the number of branch points N (11)**, both settable by the coordinator until the freeze.
- **No interim looks.** The cutoff time and N are set in the config before the scored run. No analysis of scored branches is run before the cutoff; progress is monitored by counts of finished points and voids only.
- Scrubbed containers (base-commit history only); a failed scrub voids the point.
- Fixed point order: sha256 of `plug-agent-2:<instance_id>`; all branches of a point finish before the next point starts on that server.
- Hold-out: round 3's 40 scored repositories do not occur in the pool.

## Known mistake and repeat (frozen)

- **Key = the normalized error line.** The failed command's error line (`lessons.error_line` of its output) is passed through the frozen normalizer `scripts/routea/plug_agent2_errorline.py` (tested, hash pinned in the config), which masks ANSI codes, timestamps, UUIDs, hex addresses, temp names (`tmp...`), paths, line and column numbers, and numbers of five digits or more, collapses spaces and cuts at 200 characters. A line that is empty or only placeholders after masking has no key and is excluded.
- A **known mistake** is a failed command whose normalized error line equals that of a lesson **labeled `applies` for this task** (same repository). The same function normalizes the lessons' and the agent's lines.
- **Branch point:** the first known mistake in the source run. The branch starts from the container state **just before** the command that erred (everything before it replayed, with the effects it had in the source run) and the history before the turn that issued it; the arms then choose their next commands freely for W = 15 model calls.
- **Outcome ("repeat", in the sense of repeating a mistake already recorded in an earlier session's lesson):** the same normalized error line occurs within the branch's W = 15 model calls. The `none` arm's occurrence rate is the base rate; it is high by construction at these points, because the line occurred in the source run [hypothesis].
- **Pre-registered split of the class:** a point is *generic environment* if its normalized line matches the rule `GENERIC_ENVIRONMENT` in the same file (ModuleNotFoundError or ImportError at the start of the line; command not found; not found in PATH; externally-managed-environment; no matching distribution or version; permission denied; network unreachable; connection refused; name resolution; certificate verification; no space left; a missing `pip`, `python`, `pytest`, `git`, `make`, `cmake`, `gcc`, `npm` or `node`); every other point is *code-specific*. The primary is on all points; the primary per class is reported. **If generic points dominate (more than half), every statement of the claim says so in words** ("mostly environment errors").
- **Secondary, steps lost (one definition, as coded):** the number of model calls from the first occurrence of the normalized error line in the branch to the next successful run of the same program, or to the branch's end (or W) if there is none; 0 if the error never occurs.
- The share of failures with no key and the top lines are reported from the smoke test.

## Primary outcome

**Primary (forced delivery).** Per point, the repeat share of the `forced` branches minus that of the `none` branches (6 each); the unit is the point, never the branch. The statistic is the mean over points of that difference d, tested by a **sign-flip permutation test on the mean** over points (100,000 flips, seed 0) with a BCa interval (10,000 resamples, seed 0) [established, declared now]. Points where both arms have the same share (for example 0 and 0) are ties: they stay in the mean and the sign-flip test, and their share is reported. **Expected tie share** [hypothesis]: at the probe's none-arm base rate of 0.92 per branch, 6 of 6 branches repeat at 0.92^6 = 61% of points; if the note has no effect both arms tie at about 0.61 x 0.61 = 37% of points (all-repeat in both), and ties are higher once partial equalities are counted, so most points will not discriminate and the sign-flip test has few informative points.

**Co-primary (the no-network trap): the point's program fails with ANY error within W = 15 calls**, same unit and inference. A note that only swaps one error line for another is not prevention. Replacement errors (failures of the program with a different line) are reported per arm. **Success of the primary** means both outcomes show a negative paired difference with sign-flip p below 0.05 and a BCa interval excluding zero; if only the line outcome does, the claim says the note "changed which error occurred, not whether the program failed".

**Frozen secondaries (no claims).** Primary per class (generic environment, code-specific); primary per source (own, Core); steps lost to the error; any failure with the same error class as the branch point; exit status rates. Distinct (repository, key) pairs among the points are reported, and a **sensitivity analysis uses the mean per (repository, key) cluster as the unit** (the primary stays on points; a disagreement is reported in words). Void rates are reported per source and per class (generic, code-specific).


**Gatekeeping.** The pilot's claim is made only if the primary succeeds (sign-flip p below 0.05 and the BCa interval excludes zero) and the co-primary agrees; otherwise only the estimates are reported, with no claim. No other estimate makes a claim.

- **Probe result and the pilot decision (owner, option 1).** The probe ran 4 of its 5 points: all restored, none void, and the none-arm occurrence share was 0.92 (11 of 12 branches repeated the line within 15 calls) [measured]. The 5 probe tasks are excluded from scoring. The list order is the sha256 order of `plug-agent-2:<id>`; **the cutoff is 2026-11-01 06:00 PT**; points complete at the cutoff are analyzed, and the report states how many were.

## Agent and infrastructure

- Plain Glimmer `Muse-Glimmer-30B-KQuant-17GB-Q4_K_M` (GGUF sha256 `4cc57c0f...f60e`, same as the Strix), llama.cpp 0.8.0 build 11960 (commit 8642541b2) on the owner's laptop, 2 slots of 32k, flash attention, `--jinja`; reasoning low, 4,096 tokens per reply. Containers (mini-SWE-agent, scrubbed, no network) on the 5080 CPU; from Fri 08:00 PT the same GGUF is also served by the 5080 GPU through llama.cpp (build recorded in the config), a second server, each point's branches on one server. The bearer key comes from the environment and is never logged or written to a trajectory. No judge runs in this test; the 5080 GPU stays with Core. [established]
- **Speed** [measured, one task]: about 14 tok/s generation and about 115 tok/s uncached prompt with one stream; two streams run at 8 to 9 tok/s each (about 1.25 times one slot in total); about 21 s per model call; a 53-step run took 18 min. [established]
- Images are pulled just in time with their registry size checked first (limit 8 GB, disk floor 60 GB) and removed after the point's last branch. Long drivers run detached on the 5080 with a log, a done-file and resume.

## Sizing (stated before any scored run)

- **Capacity** [hypothesis, from measured speeds]: the laptop's two slots give about 214 model calls per hour; the desktop GPU serves the same GGUF at about 21 tok/s on one stream (Core's measure), about 250 calls per hour, in the window **Fri 08:00 to Sat 08:00 PT**; about 14,500 calls in all (about 40 laptop hours, 24 desktop hours). Branches of one point run on one server; the laptop serves throughout and the desktop GPU in its window (Fri 08:00 to Sat 08:00 PT).
- **Points.** 11 in the frozen list [measured]; capacity is not the limit (12 branches of 15 calls is about 180 calls per point, so 11 points are under 2,000 calls) [hypothesis]. Because the points concentrate in 2 distinct keys, the sensitivity analysis clustered by (repository, key) has 2 clusters and cannot support an inference; it is reported only as a count.
- **Base rate and MDE.** The none-arm occurrence share was 0.92 in the probe [measured]. With the frozen SD of 0.33, the smallest detectable difference is 2.8 x 0.33 / sqrt(11) = **about 28 points** [hypothesis]: a forced note must cut a 0.9 base rate to about 0.6 to be detected. The result is a pilot and is labeled so.
